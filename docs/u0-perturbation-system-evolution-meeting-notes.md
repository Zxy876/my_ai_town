# U0、运行时微扰与人类驱动的意图版本演化

## 1. 文档定位

本文根据 `origin/agent/ews-global-u0` 分支、PR #7、Issue #18 和 Issue #19 的讨论，重新说明当前 U0 与运行时观察底座，以及它们如何发展为一个持续演化的意图版本系统。

本轮修订采用以下核心定位：

> 第一阶段不是让系统自动发现所有 Gap，也不是让系统定时生成 U+。第一阶段由人观察小镇运行、发现当前意图的执行脆弱性、向具体角色投递观察，并据此编写和晋升下一版全局意图。Builder 先托管证据和版本状态，之后再逐步接管 Gap 与候选版本提案。

因此，近期目标是实现“人类参与的意图版本演化”，长期目标才是 Builder 驱动的系统自主演化。

## 2. 当前项目已经做到什么

当前项目已经基本完成两个输入底座。

### 2.1 开局前的全局 U0

- 玩家在小镇开始运行前输入一段自然语言意图；
- 同一段 U0 会分别写入所有居民自己的长期记忆；
- U0 与存档绑定，可以在继续游戏后恢复；
- U0 在长期检索中获得基础加权；
- 由于居民身份、关系、地点和近期经历不同，同一个 U0 在不同居民记忆中的实际排名和影响可以不同；
- U0 只代表需要持续推进的共同意图，不代表意图已经被采纳或完成。

### 2.2 运行中的局部观察入口

- 玩家可以向一名具体居民投递自然语言观察；
- 观察会先成为该居民可追溯的一阶认知记忆；
- 观察可以在当前决策中参与检索、计划和行动；
- 当近期证据达到记忆整理条件时，也可能形成对自身认知脆弱性的反思；
- 反思写入后会在当前决策前重新参与检索。

### 2.3 特定例子中的直接回正

已有特定例子表明，居民不一定需要先形成反思，也可能直接通过 U0 长期记忆与新观察的共同检索，重新选择支持 U0 的行动。

准确表述应当是：

> 角色可以不依赖反思，通过记忆检索和普通认知决策直接回正。

角色仍然经历感知、记忆、检索、计划和行动，所以不能表述为“完全不经过认知循环”。反思只是条件触发的高级路径，不是每次认知更新的固定阶段。

## 3. 当前还缺少什么

现有代码还没有完整实现以下能力：

- 在同一小镇运行中创建下一版全局意图；
- 将下一版意图重新投递给所有居民；
- 明确记录当前生效的是哪一版全局意图；
- 保存全局意图版本之间的父子关系和修改原因；
- 把局部观察与后续行为变化关联起来；
- 从全体居民的记忆、计划和行动中形成全局进度视图；
- 由 Builder 自动发现 Gap、提出候选版本或执行世界能力修改。

因此，现有 U0 是开局基线，运行时观察是局部干预底座，但二者之间还缺少一个“全局意图版本覆盖层”。这正是下一阶段需要补上的核心抽象。

## 4. 统一概念

为避免把自然事件、人工输入、正负效果和全局版本混为一谈，本文采用以下概念。

### 4.1 全局意图版本 U0@vN

`U0` 表示同一条全局意图谱系，`vN` 表示这条意图在第几次迭代后的版本：

```text
U0@v0 -> U0@v1 -> U0@v2 -> ... -> U0@vN
```

- `U0@v0` 是开局前输入的初始版本；
- `U0@v1` 是人根据运行中暴露的 Gap 编写的下一版本；
- 任意时刻只能有一个正式生效的全局版本；
- 旧版本不能被删除，要保留为后续审计和回放的历史基线。

本文不再使用含义容易混淆的 `U0-1`。`U0@v1` 明确表示“同一条根意图的第一版演化”，不会被误解为 U0 减一、局部反馈或某条负向观察。

### 4.2 自然微扰 E(t)

小镇只要持续运行，就会自然产生链式因果反应：

- 角色相互邀请、拒绝、协助或发生冲突；
- 角色的个人任务与共同意图竞争；
- 地点、资源和时间条件发生变化；
- 动作成功、失败、被打断或产生意外结果；
- 新的记忆和对话继续影响后续决策。

这些运行中自然产生的事件和证据统称为 `E(t)`。它们不是系统预先生成的 U+ 或 U-，但可能使角色更加接近或更加偏离当前全局意图。

这种机制不是为某个派对示例编写的固定状态机，因此可以在不同自然语言 U0 下继续产生开放的因果变化，避免把系统过拟合到单一场景。

### 4.3 局部观察干预 I(t)

玩家向具体居民投递的一条自然语言观察统一记为 `I(t)`。

```text
I(t)：向选定居民投递一条新的可感知信息
```

它可以描述障碍、机会、他人的请求、某个事实或一种新的组织方式。输入时不需要玩家选择 U+ 或 U-，因为同一句观察对不同居民、不同世界状态可能产生不同效果。

局部观察干预不会自动成为下一版全局意图。它首先只是一次对局部认知链的介入，用于解决问题、试探系统反应，或者验证人对 Gap 的判断。

### 4.4 U+ 与 U- 是事后方向

U+、U- 不再表示两个玩家按钮，而表示同一种局部观察干预相对当前全局意图产生的正负方向。

假设 `A` 表示居民当前认知和行为对活跃全局意图的支持程度：

```text
delta_A = A_after - A_before

delta_A > 0：该观察事后表现为 U+
delta_A < 0：该观察事后表现为 U-
delta_A 约等于 0：该观察没有形成明显方向
```

第一阶段不要求系统必须自动计算出精确数值。可以先由人结合记忆、计划、行动和世界结果判断方向。后续再由 Builder 或意图追踪器提供辅助评估。

因此，“投递 U+ 或 U-”在玩家语言中应继续显示为“投递观察”；正负是研究和审计层对结果的解释。

### 4.5 Gap

Gap 是人在观察当前 `U0@vN` 的执行过程后发现的脆弱性：

> 当前角色、协作方式、能力或流程持续无法把活跃意图版本转化为合理行动和结果，并且运行证据能够说明问题发生在哪里。

第一阶段由人发现并命名 Gap，不要求系统自动预警。

Gap 可以表现为：

- 角色长期没有检索共同意图；
- 个人事项不断覆盖共同责任；
- 多名角色理解了目标，却没有形成协作；
- 人员集中、排队地点或资源分配不合理；
- 现有设施和能力不足以完成意图；
- 当前 U0 自身表达不完整，遗漏了执行中必要的约束或分工。

## 5. 第一阶段：人类驱动的意图版本演化

第一阶段的真正闭环是：

```text
开局前输入 U0@v0
-> U0@v0 分别进入所有居民的长期记忆
-> 小镇持续运行并自然产生 E(t)
-> 人观察 U0@v0 的执行进度和链式反应
-> 人发现并记录 Gap
-> 人向具体居民投递 I(t)
-> 继续观察该干预的实际方向和结果
-> 人编写 U0@v1 候选
-> 人批准并晋升 U0@v1
-> U0@v1 进入所有居民的长期记忆
-> 同一小镇继续运行
```

这里的“自身迭代”首先指系统拥有发现和承载脆弱性的能力与动机。第一阶段由人提供这种动机：人决定什么问题值得修、什么时候需要新版本、下一版意图应当保留和改变什么。

### 5.1 完全执行 U0 不是整局终点

`U0@v0` 不再被理解为整局游戏唯一且最终的目标。它是演化的起点。

一版意图在运行中可以进入以下状态：

```text
active：当前正式生效
reviewing：人正在检查执行脆弱性
candidate_ready：下一版候选已经形成
superseded：下一版晋升后，本版本成为历史基线
satisfied：当前版本的主要目标已得到满足，但小镇仍可继续演化
```

即使当前版本已经取得结果，玩家仍可以根据新的行为、问题和机会提出下一版意图。小镇无需因为 U0 被执行而结束。

### 5.2 新版本可以边做边形成

`U0@v1` 可以在 `U0@v0` 仍然运行时逐步形成。人可以先投递若干局部观察，观察它们对不同角色的作用，再整理出更好的全局意图。

但是，候选版本不能静默覆盖当前版本。在同一个观察窗口中，当前活跃版本必须保持冻结。只有人明确执行“晋升下一版意图”后，系统才建立版本边界，并把新版本作为新的全局长期记忆投递给所有居民。

这样既允许同一小镇持续运行，也能保留清晰因果关系：

```text
版本边界之前的变化，仍以 U0@v0 为参照；
版本边界之后的变化，改以 U0@v1 为参照。
```

## 6. 玩家实际需要的三个操作

玩家不需要 U0、U+、U- 三个按钮，而需要三个职责不同的操作。

### 6.1 设置开局意图

在新游戏开始前输入 `U0@v0`，并将其发给所有居民。

### 6.2 投递局部观察

小镇运行中，向某名居民投递 `I(t)`。这沿用当前已有的“投递观察”入口。

### 6.3 提出并晋升下一版共同意图

人根据全局进度、Gap 和局部观察结果编写 `U0@v(N+1)`。候选经确认后，系统建立版本边界，并把它投递给全体居民。

第三个操作目前尚未实现。它不能简单复用普通观察入口，因为普通观察只影响选定居民，而全局版本晋升必须：

- 记录父版本；
- 记录人发现的 Gap 和修改理由；
- 保存晋升时的世界时间和存档修订；
- 向所有居民投递完全相同的新版本；
- 保留旧版本及其相关记忆、决策和结果；
- 从明确边界开始切换评估基线。

## 7. U0 可以输入什么

玩家现在觉得输入模糊，不是因为缺少 U+/U- 按钮，而是系统没有解释 U0 可以承载哪些长期方向，也没有显示输入如何发展为下一版本。

U0 不只可以描述对话或一次活动，还可以描述：

- 公共活动和多人协作；
- 公共服务，例如医疗、照料和信息帮助；
- 资源组织，例如市场人流、物资和地点分配；
- 应急机制，例如事故后如何确认事实和组织协助；
- 社区规则，例如承诺、交接和替代方案；
- 长期能力方向，例如逐步形成能够处理复杂病例的医院。

较好的 U0 自然语言通常能够回答四个问题，但不要求玩家填写四个字段：

1. 希望小镇长期推进什么；
2. 哪些角色承担主要责任；
3. 遇到障碍时不能破坏什么原则；
4. 玩家可以从什么现象判断它正在取得进展。

例如：

```text
小镇需要逐步形成可靠的基础医疗服务。林岚负责接待并了解居民的问题，其他居民在发现伤病或持续不适时提供信息和协助。遇到无法处理的情况时要保留问题、确认事实并继续寻找办法，不要把建议当成已经完成的治疗。
```

即使当前世界没有足够医疗能力，这条 U0 仍然有意义，因为运行中的失败会暴露能力 Gap，并为下一版意图或后续建设提供证据。

## 8. 玩家为什么需要看到版本与证据

玩家当前只能看到自己提交了一段文字，却不容易理解它与后续演化的关系。

意图版本覆盖层至少应当让玩家看到：

- 当前活跃的全局意图版本；
- 该版本何时写入、覆盖哪些居民；
- 每名居民是否记住、检索和实际响应了它；
- 小镇运行中出现了哪些相关事件和链式反应；
- 人已经记录了哪些 Gap；
- 向哪些居民投递过什么观察；
- 观察之后的计划、行动和世界结果发生了什么变化；
- 下一版候选保留了什么、修改了什么、为什么修改；
- 新版本何时晋升，旧版本何时退出活跃状态。

第一阶段不需要系统自动替人判断所有这些关系。只要把证据按角色、时间和意图版本组织起来，人就可以完成观察和迭代。

## 9. 控制变量实验的正确位置

控制变量实验仍然重要，但它是验证系统机制的方法，不是默认游戏流程。

### 9.1 验证局部观察的效果

从同一个 `U0@vN` 存档修订分出两组：

```text
control：不投递局部观察，保持自然运行。
intervention：在相同时间向相同居民投递同一条 I(t)。
```

对比两组中该居民的记忆、计划、行动、反思和世界结果，判断观察的实际方向。不能仅凭输入文字预先断言它一定是 U+ 或 U-。

### 9.2 验证下一版全局意图

从同一个版本边界分出两组：

```text
current：继续使用 U0@vN。
next_version：晋升人编写的 U0@v(N+1)，并投递给全体居民。
```

对比两组是否在相同或相似微扰下产生不同协作和结果，从而判断新版本是否真的改善了原 Gap。

### 9.3 后续自动 EWS 实验

当未来开始研究自动 Gap 检测和自动回写时，仍可以使用三组实验：

```text
control：只有当前意图版本。
perturbed：加入同一可控微扰，不进行回写。
corrected：加入同一微扰，并由系统根据证据生成恢复观察。
```

这属于后续自动化验收，不应被误写成第一阶段玩家必须按固定时序输入 U- 和 U+。

### 9.4 实验记录

实验至少记录：

| 观察项 | 需要回答的问题 |
| --- | --- |
| 活跃版本 | 当前以哪一版 U0 为参照 |
| 全局记忆 | 新版本是否分别进入所有居民长期记忆 |
| 局部观察 | 原文、目标居民、投递前后的世界状态 |
| 检索 | 居民是否召回当前版本和相关观察 |
| 计划与行动 | 是否出现可观察变化，世界是否接受行动 |
| 反思 | 是否发生，引用了哪些真实证据 |
| Gap | 谁发现、依据什么、影响哪个版本 |
| 方向 | 干预结果更支持、更竞争还是基本无关 |
| 版本晋升 | 父版本、修改理由、批准人和边界时间 |
| 客观结果 | Gap 是否真的减少，而非只改变了文本 |

真实模型存在随机性，同一条件需要重复运行，不能用一次成功结果直接证明稳定因果关系。

## 10. 示例：欢迎派对从 U0@v0 演化到 U0@v1

### 10.1 开局意图 U0@v0

```text
今天傍晚，全镇居民要在独立市集共同举办欢迎派对。林岚负责确认场地和灯光，唐小满负责桌椅，花子负责邀请居民。遇到障碍时先确认事实并调整计划，不要把计划当成已经完成。
```

这条意图在开局前分别进入所有居民长期记忆。小镇开始后，花子可能主动寻找居民交谈；被邀请的居民会把对话、U0 和自己的近期记忆一起检索，再决定是否协助。

### 10.2 自然链式微扰

运行中可能出现：

```text
受邀居民都从市集北侧入口到达，桌椅也堆在入口附近，排队和人群越来越集中；广场中央仍然空着。
```

这不是系统自动生成的 U-，而是 U0 执行过程中自然产生的链式结果。

### 10.3 人发现 Gap

玩家观察后提出：

```text
Gap：当前共同意图只规定了邀请、桌椅和灯光责任，没有说明集合位置和人流分散方式，导致所有协作集中在错误位置。
```

### 10.4 向具体角色投递观察 I(t)

玩家先向负责邀请的花子投递：

```text
花子看到北侧入口已经排起长队，而广场中央仍有足够空间。她可以把这个情况告诉正在到达的居民，并确认大家是否改在广场中央集合。
```

这条观察在输入时不需要标成 U+。只有观察花子后续是否传播信息、其他居民是否改变集合地点、人群是否分散，才能判断它实际产生了正向、负向还是无明显效果。

### 10.5 人编写 U0@v1 候选

根据当前 Gap 和局部观察效果，玩家提出下一版共同意图：

```text
全镇共同活动除明确邀请、桌椅和灯光负责人外，还要确认主要集合区域和人流分散方式。负责人发现入口拥堵或资源集中错误时，应先把现场事实通知相关居民，再共同调整集合位置和分工。
```

### 10.6 晋升并继续运行

玩家确认后，系统把该候选晋升为 `U0@v1`，记录它来自 `U0@v0` 的“集合位置和人流组织 Gap”，并将新版本分别写入所有居民长期记忆。

小镇不需要重新开局。后续发生的新事件以 `U0@v1` 为当前基线，并可能继续暴露新的 Gap，形成 `U0@v2`。

## 11. Builder 的分阶段定位

Builder 不应一开始就替人决定 Gap 和下一版意图。更稳妥的路线是逐步移交。

### 阶段 0：人就是 Builder

- 人观察全局进度；
- 人发现和命名 Gap；
- 人选择需要接收局部观察的居民；
- 人编写并批准下一版全局意图；
- 系统只负责记录、投递、版本边界和回放。

### 阶段 1：Builder 托管状态流转

Builder 作为全局控制层协助：

- 汇总全体居民的相关记忆、计划、行动和世界结果；
- 控制运行速度，在需要审查时暂停或减速；
- 提醒玩家当前存在未处理证据；
- 管理 Gap、局部观察、候选版本和晋升状态；
- 生成比较摘要，但不擅自决定新版本。

建议状态流为：

```text
RUNNING U0@vN
-> HUMAN REVIEW
-> GAP RECORDED
-> LOCAL OBSERVATION
-> EFFECT REVIEW
-> NEXT VERSION DRAFT
-> HUMAN APPROVAL
-> PROMOTE U0@v(N+1)
-> RUNNING U0@v(N+1)
```

### 阶段 2：Builder 提出候选

- Builder 根据跨角色证据提出候选 Gap；
- Builder 建议目标居民和局部观察；
- Builder 起草 `U0@v(N+1)`；
- 人负责修改、批准或拒绝。

### 阶段 3：受约束的自主演化

- Builder 在明确权限和允许动作范围内自动推进低风险迭代；
- 高风险意图修改、世界能力变化和回滚仍由人批准；
- 所有自动提案、执行和结果继续保留证据链。

Builder 可以在界面中被表现为一个全局角色，但它在架构上属于控制层，不能伪装成普通居民。普通居民只能读取自己的记忆和本地感知；Builder 才能读取跨角色证据、托管版本状态和控制审查节奏。

## 12. 从意图版本演化到完整系统演化

需要区分三个层级：

```text
局部认知干预：向具体居民投递观察并观察行为变化。

意图版本演化：人根据 Gap 把 U0@vN 修订并晋升为 U0@v(N+1)。

完整系统演化：根据重复 Gap 修改设施、角色能力或工作流程，形成新世界版本，并验证 Gap 减少。
```

第一阶段实现意图版本演化，就已经把原本“一局只执行一条 U0”变成了“一局围绕 U0 持续发现脆弱性并产生新版本”。这是完整系统演化之前必要的纸原型和控制层。

医院场景以后可以沿用同一结构：

```text
U0@v0：小镇形成基础医疗服务
-> 运行中出现病例和自然微扰
-> 人发现诊断、排队或协作 Gap
-> 向医生或相关居民投递局部观察
-> 人形成 U0@v1 候选
-> Builder 托管版本和证据
-> 后续 World Mutation Adapter 执行能力或设施变化
-> 验证同类 Gap 是否减少
```

如果只产生一段更好的意图文本，这是意图版本演化；当新版本进一步驱动了可执行能力或流程改变，并验证了行为和结果变化，才成为完整系统演化。

## 13. 近期实现顺序

### 里程碑 1：补上全局意图版本覆盖层

- 显示当前 `U0@vN`；
- 允许人创建下一版候选；
- 保存父版本、Gap、修改理由和创建者；
- 由人明确晋升；
- 在同一小镇中把新版本投递给所有居民；
- 保留旧版本及其存档和 Trace。

### 里程碑 2：建立人类观察工作台

- 按当前意图版本聚合居民记忆、计划、行动和世界结果；
- 允许人记录 Gap；
- 把局部观察与投递后的变化关联起来；
- 允许人判断观察的事后正负方向；
- 支持从固定存档进行对照和回放。

### 里程碑 3：加入 Builder 状态托管

- 托管运行、审查、Gap、干预、候选和晋升状态；
- 控制模拟速度与审查点；
- 汇总证据但保留人的最终决定权。

### 里程碑 4：逐步自动化

- Builder 提出 Gap 和候选版本；
- 人审核；
- 在证据充分且权限允许时执行能力或流程变化；
- 从新世界版本验证 Gap 是否减少。

## 14. 课后作业修订版

1. 选择一条不局限于简单对话、能够在运行中暴露协作或能力问题的 `U0@v0`。
2. 确认它分别进入所有居民长期记忆，并记录不同角色的检索和行动差异。
3. 不预设固定时间输入 U+ 或 U-，让小镇先自然运行并产生链式微扰。
4. 由人观察当前版本的执行进度，记录一个有具体证据的 Gap。
5. 向一名相关居民投递一条自然语言观察，记录投递前后的记忆、计划、行动和世界结果。
6. 根据实际效果判断该观察相对当前版本是正向、负向还是基本无关。
7. 由人根据 Gap 和干预结果编写 `U0@v1` 候选，说明保留了什么、改变了什么。
8. 在明确版本边界上晋升 `U0@v1`，向所有居民投递，并让同一小镇继续运行。
9. 对比版本晋升前后的行为变化，判断原 Gap 是否减少，以及是否暴露了新 Gap。
10. 完整保存存档修订、意图版本、局部观察、记忆节点、决策 Trace、反思和世界结果。

## 15. 最终判断

修订后的发展方向贴合项目现实，并且比“自动 U+ 回正优先”更适合作为下一阶段：

- U0 是一条可持续演化的全局意图谱系，而不是整局唯一终点；
- 小镇自然运行会产生开放的链式微扰，不需要为每种场景预设偏离；
- 玩家只有一个局部观察入口，U+、U- 是干预后的实际方向；
- 第一阶段由人发现 Gap、投递观察、编写和晋升新版本；
- 同一小镇可以从 `U0@v0` 持续演化到 `U0@vN`，但每次晋升必须有明确版本边界；
- Builder 先接管证据和状态流转，再逐步接管 Gap 与候选版本提案；
- 完全自主的系统演化建立在这条人类驱动闭环已经可观察、可回放、可比较的基础上。

近期最关键的开发不是增加 U+、U- 按钮，也不是立刻开发医院 Builder，而是补上当前缺失的第三种操作：

```text
人根据运行证据提出下一版共同意图
-> 明确批准并建立版本边界
-> 在同一小镇中投递给所有居民
-> 继续观察下一轮脆弱性
```
